## 作业 1

1. 什么是多道程序设计？多道程序设计与分时系统的区别是什么？
   - 多道程序设计：指在内存中同时存放多道作业，使它们共享 CPU 和外部设备。当一道程序因等待 I/O 而暂停执行时，CPU 立即转去执行另一道程序，从而提高资源利用率和系统吞吐量。
   - 主要区别：
     * **目标不同：** 多道程序设计的主要目标是**提高 CPU 利用率**；分时系统的目标是**提高人机交互性**，使用户感觉自己独占计算机。
     * **调度方式：** 多道程序设计通常在程序遇到 I/O 阻塞时才切换；分时系统引入了**时间片**概念，强制程序在规定时间内轮流使用 CPU。

2. 什么原因推动了操作系统从批处理发展到多道程序，进而发展到分时系统？
   * **批处理 $\rightarrow$ 多道程序：** 主要是为了解决 **CPU 与 I/O 设备速度不匹配**的问题。单道批处理中 CPU 经常处于等待 I/O 的闲置状态，多道程序通过“交替执行”大幅提升了硬件利用率。
   * **多道程序 $\rightarrow$ 分时系统：** 主要是为了满足**用户交互**的需求。多道程序系统下，用户无法在程序运行期间进行干预，调试困难；分时系统通过快速切换，提供了实时响应能力。

3. 什么是陷阱？与中断的区别是什么？什么是系统调用？
   * **陷阱：** 是一种**内部中断**，通常由软件引起（如执行了非法指令、地址越界或显式调用陷阱指令）。
   * **与中断的区别：** 陷阱是**同步**的，由当前执行的指令触发；中断（通常指外部中断）是**异步**的，由外部硬件设备产生，与当前指令执行无关。
   * **系统调用：** 是操作系统提供给应用程序的接口，允许用户程序请求内核服务（如读写文件、创建进程）。它通常通过触发一个特定的陷阱来实现从用户态到内核态的切换。

4. 关于操作系统的可移植性
   * 判断： 错误。可移植的操作系统在迁移到不同架构时，通常仍需要进行少量底层代码的修改或重新编译。
   1) 为什么完全可移植是不可能的？ 因为操作系统必须直接与硬件交互。不同架构的指令集 (ISA)、内存管理单元 (MMU) 结构、中断处理机制和寄存器定义各不相同，这些底层相关的代码无法直接在异构硬件上运行。
   2) 高度可移植系统的两个设计层次：
      1.  **硬件抽象层 (HAL):** 将所有与硬件直接相关的操作（如时钟管理、中断分配）封装在此层，屏蔽底层差异。
      2.  **内核核心/体系结构无关层:** 处理进程调度、文件系统等逻辑逻辑，这部分代码使用高级语言（如 C）编写，无需修改即可在不同架构间复用。


5. 矛盾的设计实例
   * **资源利用率 vs. 健壮性：** 为了追求极高的资源利用率，系统可能会减少冗余校验和隔离保护，但这会导致系统在某个组件出错时更容易崩溃，降低了健壮性。
   * **吞吐量 vs. 响应时间：** 增加时间片长度可以减少进程切换开销，从而提高系统总吞吐量，但这会导致单个用户的响应时间变长，影响交互体验。

6. 最简单的启动过程功能总结
   一个最简化的系统启动（Bootstrap）至少需要具备以下功能：
   1.  **硬件初始化：** 检查并配置基本的硬件环境（如内存、CPU 状态）。
   2.  **加载引导程序：** 从预定义的固定位置（如磁盘首扇区）将操作系统内核的一部分或引导加载程序读入内存。
   3.  **跳转执行：** 将控制权交给内核入口点，开始执行操作系统内核程序。

### 2. 地址概念解释
* **逻辑地址:** 程序员在源码中使用的地址（如变量名或汇编中的偏移量），由CPU生成。
* **物理地址:** 内存单元的真实单元地址，是加载到内存地址寄存器中的最终地址。
* **地址映射:** 将逻辑地址转换为物理地址的过程（通常由MMU硬件完成）。
    * **例子:** 在页式管理中，逻辑地址 `页号 + 页内偏移` 通过页表查找到物理块号，拼接成物理地址。

### 3. 页表、段表与快表
* **设置原因:** 解决内存碎片问题，实现离散分配。**页表/段表**记录了逻辑单元与物理单元的映射关系。**快表 (TLB)** 是一种高速缓存，用于存放常用页表项，以加速地址转换（减少访问内存次数）。
* **转换过程:** 逻辑地址 $\rightarrow$ 提取页号 $\rightarrow$ **查TLB**（若命中则直接获取物理块号；若不命中则查内存页表） $\rightarrow$ 结合页内偏移 $\rightarrow$ 生成物理地址。


### 4. 缺页中断处理流程

1. 处理器向MMU发送虚拟地址
2. MMU从内存获取页表项
3. 有效位为0，MMU触发缺页异常
4. Handler用需要的页面替换特定页
5. Handler返回最初进程，重启引发缺页中断的指令

### 5. 多级页表计算

**(1) 优点:** **节省内存**，只有当前需要的页表才会被调入内存。对于稀疏的虚拟地址空间，不需要为整个空间预留全部页表空间。
**(2) 计算:**
* 页面大小 = 16KB = $2^{14}$ B，则**页内偏移位 = 14位**。
* 剩余位数 = 38位 - 14位 = 24位（用于页表索引）。
* 页表项大小 = 4B，一个页面能容纳 $16KB / 4B = 2^{12}$ 个项。
* 为了使一级、二级页表刚好各占一个页面，分配如下：
    * 第二级页表索引 = 12位
    * 第一级页表索引 = 24 - 12 = 12位

### 6. 页面置换算法思考

**(1) 效果评估:** 
将物理页框数设为 $m$
情况 A：$m \ge 512$ (内存充足)
* **表现**：非常优秀
* **分析**：
    * 一旦预热完成（即 0-511 号页面都已调入内存），整个循环序列都会驻留在内存中。
    * **LRU/FIFO/Clock** 都能实现循环部分 100% 的命中率。
    * 只有在周期之间出现的“随机页面”可能会导致少量的缺页中断，但由于内存空间足够，这些算法都能很好地处理。

情况 B：$m < 512$ (内存不足，如题目第二小题提到的 500)
* **表现**：**极差（发生颠簸）**。
* **分析**：
    * 当 $m < 512$ 时，这三种算法都会在循环访问中表现出“最差性能”。
    * **LRU**：在循环到第 $m+1$ 个页面时，会把第 1 个页面踢出，而第 1 个页面恰恰是下一个周期最先需要的。这会导致**每一次循环访问都发生缺页**（如果忽略随机访问的干扰）。
    * **FIFO/Clock**：同样遵循类似的换出逻辑，在处理步长为 1 的大循环时，命中率会趋近于 0。



**(2) 优化算法:** 
针对性改进
策略：固定其中的 499 个页面。

具体设计：
将 499 个页框永久分配给循环序列的前 499 个页面（0-498）。
剩下的 1 个页框用来轮换处理剩余的页面（499-511 以及随机页面）。

### 7. 伙伴系统 (Buddy System)

合并过程: 当释放一个大小为 $2^k$ 的块时，系统检查其伙伴块是否也空闲。若是，则合并成一个 $2^{k+1}$ 的块，并递归向上尝试合并。
伙伴条件:
1. 大小相同。
2. 物理地址连续。
3. **对齐要求:** 从同一个更大的块拆分出来的（起始地址满足 $Address \pmod{2^{k+1}} = 0$）。

### 8. EAT 计算

(1) 最佳情况 (TLB Hit + Cache Hit):
$$Time = 10ns + 5ns = 15ns$$

(2) 平均内存访问时间 (EAT):

* 访问内存/Cache项的平均时间 $E_a = h_c \times t_c + (1-h_c) \times (t_c + t_m) = 0.98 \times 5 + 0.02 \times 105 = 4.9 + 2.1 = 7ns$。
* 获取页表项(PTE)的平均时间 $E_p = h_t \times t_b + (1-h_t) \times (t_b + 2 \times E_{mem}) = 0.95 \times 10 + 0.05 \times (10 + 2 \times 7) = 9.5 + 1.2 = 10.7ns$。
* $EAT = E_p + E_a = 10.7ns + 7ns = 17.7ns$。

## 作业 4

### 1. 读者写者问题

```c
int readcount = 0;      // 正在读的读者数量
int writecount = 0;     // 正在等待或准准备写的写者数量
Semaphore r_mutex = 1;  // 保护 readcount
Semaphore w_mutex = 1;  // 保护 writecount
Semaphore read_lock = 1;// 控制读者进入的栅栏（有写者时堵住读者）
Semaphore resource = 1; // 资源访问互斥锁（读写互斥、写写互斥）

Writer() {
    P(w_mutex);
    if (++writecount == 1) P(read_lock); // 第一个写者到达，封锁读者流
    V(w_mutex);

    P(resource);        // 互斥访问资源
    // --- 执行写操作 ---
    write();
    V(resource);

    P(w_mutex);
    if (--writecount == 0) V(read_lock); // 最后一个写者离开，释放读者流
    V(w_mutex);
}

Reader() {
    P(read_lock);       // 检查是否有写者在等待（如有，则在此排队）
    P(r_mutex);
    if (++readcount == 1) P(resource);   // 第一个读者占用资源锁
    V(r_mutex);
    V(read_lock);       // 释放栅栏，允许后续读者进入

    // --- 执行读操作 ---
    read();

    P(r_mutex);
    if (--readcount == 0) V(resource);   // 最后一个读者释放资源锁
    V(r_mutex);
}
```

### 3. 进门问题

```c
int count = 0;
Semaphore mutex = 1;    // 保护 count
Semaphore barrier = 0;  // 等待所有人刷卡
Semaphore door = 1;     // 保证一个一个过大门

Employee() {
    // 阶段1：刷卡同步
    P(mutex);
    count++;
    if (count == 5) V(barrier); // 第5个人唤醒第一位开始进入
    V(mutex);
    
    P(barrier);         // 等待信号
    V(barrier);         // 传递信号给下一个同事

    // 阶段2：一个一个过大门
    P(door);
    // --- 通过大门 ---
    pass_door();
    V(door);

    // 阶段3：最后一人关门
    P(mutex);
    count--;
    if (count == 0) {
        // 关门操作
        close_door();
    }
    V(mutex);
}
```

### 4. 搜索-插入-删除问题

```c
int scount = 0;         // 搜索者数量
Semaphore r_mutex = 1;  // 保护 scount
Semaphore i_mutex = 1;  // 插入者之间的互斥
Semaphore s_d_lock = 1; // 搜索与删除的互斥
Semaphore i_d_lock = 1; // 插入与删除的互斥

Searcher() {
    P(r_mutex);
    if (++scount == 1) P(s_d_lock); // 第一个搜索者阻止删除
    V(r_mutex);
    
    // --- 执行搜索 ---
    search();
    P(r_mutex);
    if (--scount == 0) V(s_d_lock); // 最后一个搜索者释放删除
    V(r_mutex);
}

Inserter() {
    P(i_mutex);      // 插入者之间互斥
    P(i_d_lock);     // 阻止删除
    
    // --- 执行插入 ---
    insert();
    V(i_d_lock);
    V(i_mutex);
}

Deleter() {
    P(s_d_lock);     // 确保没有人在搜索
    P(i_d_lock);     // 确保没有人在插入
    
    // --- 执行删除 ---
    delete();
    V(i_d_lock);
    V(s_d_lock);
}
```

### 5. 公园购票问题

```c
int readcount = 0;      // 当前正在查询的人数
int quota = N;          // 剩余票数
Semaphore rmutex = 1;   // 保护 readcount 变量的互斥访问
Semaphore mutex = 1;    // 保护 quota 变量（写操作）的互斥访问
Semaphore in = 1;       // 保证购票者和查询者按到达顺序排队的“大门”信号量

// --- 购票者 B (相当于写者) ---
buy() {
    // 第一次检查：如果已经没票，直接返回
    if (quota == 0) {
        print("sold out!");
        return;
    }

    P(in);          // 步入排队区，保证顺序
    P(mutex);       // 申请对票数 quota 的独占访问权

    // 第二次检查：在获取锁后再次确认余票（防止在等待锁时票被买光）
    if (quota == 0) {
        print("sold out!");
        V(mutex);   // 注意释放锁
        V(in);
        return;
    } 
    else {
        quota--;    // 执行写操作：扣减票数
    }

    V(mutex);       // 释放票数锁
    V(in);          // 离开排队区
}

// --- 查询者 Q (相当于读者) ---
query() {
    P(in);          // 步入排队区，按序等待
    P(rmutex);      // 保护 readcount 的修改

    if (++readcount == 1) {
        P(mutex);   // 第一个查询者要占住 quota 锁，防止购票者修改
    }

    V(rmutex);
    V(in);          // 释放排队锁，允许后续的人（包括购票者）排队

    read the "quota"; // 执行读操作：查看余票

    P(rmutex);
    if (--readcount == 0) {
        V(mutex);   // 最后一个查询者离开，释放 quota 锁
    }
    V(rmutex);
}
```

### 2. 死锁讨论

结论：该系统不会发生死锁。
理由：
死锁发生的必要条件之一是“循环等待”。
假设系统处于死锁状态，意味着所有 $n$ 个进程都在等待资源，且每个进程至少已持有一台打印机（否则它不会进入等待状态）。
设 $x_i$ 为进程 $i$ 已持有的打印机数，$y_i$ 为其还需要的打印机数。
在死锁状态下，所有打印机已被分配且无法满足任何进程的进一步需求：
1. $\sum x_i = m$ （所有资源已分配完毕）
2. 每个进程都在等待，故 $y_i \geq 1$。

由此可得：$\sum x_i + \sum y_i \geq m + n$。
但已知条件给出 $\sum (\text{已分配} + \text{还需要}) < m + n$，这与死锁的假设矛盾。
因此，至少存在一个进程 $k$，其 $y_k = 0$（即不再需要额外打印机），该进程可以执行完毕并释放资源，从而打破死锁风险。

### 3. 动态优先级设计

(1) 饥饿现象原因：
如果只使用静态的 `nice` 值作为优先级，当系统中不断有 `nice` 值很小（优先级高）的新进程加入时，`nice` 值较大（优先级低）的进程将永远无法获得 CPU，导致“饥饿”甚至“饿死”。

(2) 动态优先级设计：
设计公式：$Priority = nice + cpuTime - waitTime$
(注：结果越小优先级越高)

`waitTime`（等待时间）的作用：随着进程在就绪队列中等待时间变长，`waitTime` 增大，导致 `Priority` 数值减小（优先级提高）。这保证了任何进程无论初始优先级多低，最终都能因为等待时长足够久而获得执行机会，从而避免饥饿。

### 4. 同步与互斥

* 同步关系：指多个进程为了完成同一个任务，在执行次序上产生的协作关系。一个进程的执行依赖于另一个进程发送的信号或完成的结果。
* 互斥关系（Mutual Exclusion）：指多个进程因争用临界资源（如打印机、共享变量）而产生的制约关系。当一个进程进入临界区访问资源时，其他由于该资源而请求进入临界区的进程必须等待。

### 3. 场景选择与理由

场景 A（读取键盘单个字符）：中断驱动方式。
理由： 键盘输入速度极慢且具有随机性。由于数据量极小（1字节），不值得用 DMA；而中断驱动能让 CPU 在没有按键时处理其他任务，不必忙等，提高效率。

场景 B（读取磁盘 4KB 文件块）：DMA 方式。
理由： 磁盘是块设备，数据传输以块为单位，数据量较大且速率较快。DMA 可以在不占用 CPU 的情况下将一整块数据直接传送到内存，仅在传输结束时触发一次中断通知 CPU。

场景 C（连续打印 100 页文档）：通道控制方式（或 DMA 方式，取决于系统复杂度）。
理由： 面对大量且连续的输出任务，通道控制方式可以执行专门的通道指令，自主管理复杂的数据传输逻辑，最大程度释放 CPU，使其专注于计算而非管理频繁的打印任务。

### 4. 路径命名与设备独立性

(1) 程序变化：
*   物理命名： 程序会失效。因为路径中包含了具体的硬件设备名 `sda1`，硬件更换为 `nvme0n1` 后，原路径无法找到文件。
*   逻辑命名： 程序正常运行。逻辑命名通过挂载点屏蔽了底层硬件差异，用户程序无感知。

(2) 推荐方式：逻辑命名。
*   理由： 操作系统追求设备无关性。使用逻辑命名可以将用户程序与物理设备解耦，当硬件升级、维护或更换接口时，无需修改应用程序，提高了系统的可维护性和程序的移植性。

### 5. 缓冲区计算

*   单缓冲：
    *   第一块准备好并传送到用户区需 $4+1=5$ms，此时 CPU 开始处理（2ms），同时开始读第二块。因为 $T > C$，每块的处理瓶颈在 $T$。

### 6. SPOOLing 技术

原理： SPOOLing（外部设备联机并行操作）在磁盘上开辟输入井和输出井。
*   打印示例： 当多个用户进程请求打印时，系统并不直接把物理打印机分配给进程（打印机是独占设备）。系统接收打印请求后，将数据快速存入磁盘的“输出井”中并排队。
*   效果： 对用户进程而言，打印操作似乎已“立即可用”并完成；而物理打印机则在后台由 SPOOLing 管理程序按顺序依次打印。这样就把一台独占的物理设备虚拟成了多台可并发使用的逻辑设备。

### 7. 同步 I/O 与 异步 I/O
*   核心区别： 阶段 2（数据从内核拷贝到用户空间）是否会导致进程阻塞。
*   同步 I/O： 在阶段 1 结束后，进程在阶段 2 必须亲自参与或等待拷贝完成，即拷贝过程中进程是阻塞的，直到数据进入用户空间。
*   异步 I/O： 进程发起请求后立即返回。阶段 1 和阶段 2 全由系统完成。进程只需等系统通知“数据已在用户空间就绪”即可，在整个 I/O 期间，进程都在执行其他任务。

### 2. RAID

在采用 RAID 0+1 的系统中，共有 $2\times n$ 块磁盘，分为两组，每组有 $n$ 块磁盘。
* 每组内部采用 RAID 0（条带化），只要组内的任意一块磁盘故障，整组 RAID 0 就会失效。
* 两组之间采用 RAID 1（镜像），Group 1 与 Group 2 互为镜像备份。

1. 故障情况计算：
   
* 系统中共有 $2n$ 块磁盘，随机出现 2 块磁盘故障的总组合数为：
  $$C_{2n}^{2} = \frac{2n(2n-1)}{2} = n(2n-1)$$

2. 数据未丢失的概率：
   
* 要想数据不丢失，必须保证发生故障的两块磁盘刚好属于同一组。
* 2 块故障盘在同一组的组合数为：

  $$C_{n}^{2} + C_{n}^{2} = 2 \times \frac{n(n-1)}{2} = n(n-1)$$
* 不发生数据丢失的概率为：

  $$P_{\text{安全}} = \frac{n(n-1)}{n(2n-1)} = \frac{n-1}{2n-1}$$

3. 发生数据丢失的概率 (求发生的概率)：
   
   $$P_{\text{丢失}} = 1 - P_{\text{安全}} = 1 - \frac{n-1}{2n-1} = \frac{(2n-1) - (n-1)}{2n-1} = \frac{n}{2n-1}$$

### 3. 文件系统性能

提高文件系统性能主要可以从以下五个方面进行：

1. 引入内存高速缓存（Caching）
   * 块/页高速缓存：在内存中缓存常用磁盘块，避免重复读盘。
   * 延迟写与合并写：在内存中攒够数据后再批量写入磁盘，减少写盘次数。
   * 提前读取：利用局部性原理，顺序读文件时提前将后继块读入缓存。

2. 优化磁盘布局与局部性（Locality）
   * 块组/柱面群技术：将文件的 inode、数据块及其所在目录分配在同一个物理区域，减少磁头寻道。
   * 区分配（Extent）：使用连续物理块分配（如 Ext4、NTFS），减少文件碎片，提升顺序读写速度。
   * 目录项与 FCB 分离：使目录块能装下更多目录项，加速路径解析。

3. 改进磁盘移臂调度（Disk Scheduling）
   * 采用 SSTF、SCAN（电梯算法） 或 CSCAN 对磁盘请求队列进行重新排序，最小化磁头寻道时间和延迟。

4. 加速目录检索与路由（Path Lookup）
   * 路径缓存（dentry cache）：在内存中缓存解析好的目录路径映射，避免重复逐级读盘检索。
   * 高级数据结构：在大型目录中使用 哈希表（Hash） 或 树状结构（B-Tree） 代替线性拉链，实现快速定位。

5. 采用快速一致性机制（Journaling）
   * 日志文件系统：通过先顺序写日志区、再异步写入数据区的方式提高写入效率，并在系统崩溃后实现秒级快速恢复。
