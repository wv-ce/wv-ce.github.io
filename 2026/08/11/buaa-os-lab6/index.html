Thinking 6.3

  1. PIPE_SIZE 过小有什么影响？
    PIPE_SIZE 过小会导致管道缓冲区很容易满或空。
    写者可能很快因为缓冲区满而阻塞，读者也可能很快因为缓冲区空而阻塞，从而造成频繁的睡眠、唤醒和进程切换，降低系统效率。

  2. 缓冲区大小如何影响吞吐和切换效率？
    缓冲区越大，一次能缓存的数据越多，读写进程可以连续运行更久，减少阻塞和进程切换次数，因此吞吐率更高、切换效率更好。
    缓冲区越小，读写双方越容易频繁等待，进程切换次数增加，吞吐率下降。
    但缓冲区也不是越大越好，过大会浪费内存资源。

Thinking 6.4

不恒成立。

由于 pageref 不是原子操作且涉及多次系统调用。

  • 在执行 fork、dup、close 等改变引用计数的过渡期间，等式两边会因计数更新先后顺序不一而失衡。
  • 在用户态分次查询 pageref 之间若发生进程切换，获取到的状态可能不一致。

会造成短暂误判。
例如，读进程可能在写端尚未完全关闭时，因计数暂时平衡而误判定管道已关，从而提前返回 EOF，导致读取数据不完整。

Thinking 6.5

  • 假设一个进程拥有管道的读端 p[0] 和写端 p[1]。此时：pageref(p[0]) = 1, pageref(p[1]) = 1, pageref(pipe) = 2。
  • 该进程调用 dup(p[0], newfd) 试图复制读端描述符。
  • dup 函数刚刚完成了 文件描述符页 (Fd 页) 的映射（即执行完映射 oldfd 到 newfd 的 syscall_mem_map），但尚未开始映射 数据页 (Pipe 页)。此时产生时钟中断，进程切换。
  • 此时：
    • pageref(p[0]) 因为刚刚的 dup 操作已经增加到了 2。
    • pageref(p[1]) 依然是 1。
    • pageref(pipe) 因为对应的物理页尚未被 newfd 重新映射，其引用计数依然是 2。
  • 同时，另一个参与通信的读进程（或当前进程被调度回来后）执行 read。read 首先判断写者是否全部关闭。它会发现：pageref(p[0]) 的值是 2，而 pageref(pipe) 的值也是 2。pageref(pipe) == pageref(p[0]) 成立，读进程误认为写端已经全部关闭，从而直接退出或返回 EOF，导致数据读取不完整，出现了预想之外的情况。

Thinking 6.7

  1. 能否解决及其分析：
    可以解决。
    若先 unmap fd 再 unmap pipe，在两次操作的间隙，fd 的引用计数先减少，使得 pageref(pipe) > pageref(fd) 依然成立。这样就不会触发 _pipe_is_closed 中“两者相等”的误判条件，从而消除了竞争风险。

  2. dup 中的类似问题：
    会出现类似问题。
    dup 是增加引用的过程。如果先映射（增加）fd 页，再映射 pipe 页，在两者之间的间隙，fd 的引用计数已经加 1 而 pipe 计数未变，这会使 pageref(fd) == pageref(pipe) 提前成立。这会导致读进程误以为写端已关闭。
    解决方法： 模仿 close 的逻辑，dup 应该先映射 pipe 页面，再映射 fd 页面。

Thinking 6.8

1. 打开文件的过程

打开文件是一个通过 IPC（进程间通信）与文件系统服务进程交互的过程：

  1. 用户态请求：用户进程调用 open，触发 fsipc_open。
  2. IPC 通信：fsipc_open 向文件系统服务进程发送请求。
  3. 服务端处理：服务端通过 serve_open 查找对应的文件控制块（FCB），并申请 struct Open 结构记录文件状态。
  4. 建立映射：用户进程申请 struct Filefd，并通过共享页面的方式访问文件系统进程中的数据，同时调用 map 将对应的磁盘块映射到内存中。

2. 读取并加载 ELF 文件

加载 ELF 的核心在于解析其结构并进行地址映射：

  1. 验证头部：检查 ELF Magic Number，确认文件合法。
  2. 解析表项：根据文件头（ELF Header）的偏移量找到程序头表（Program Header Table）。
  3. 遍历段信息：遍历每一个程序头表项（Segment）。
  4. 页面映射：根据表项中定义的虚拟地址、文件偏移和长度，将段内容加载或映射到进程的虚拟内存空间中。

3. bss 段的正确加载与零初始化

.bss 段在 ELF 文件中不占空间，但在内存中需要占用空间且初值为 0。实现机制如下：

  1. 识别间隙：elf_load_seg() 会比较物理段大小（filesz）和内存段大小（memsz）。.bss 对应的就是 memsz > filesz 的部分。
  2. 分段加载：该函数将一个段分为三部分处理：
    • 开头未对齐的部分。
    • 中间包含文件内容的数据部分。
    • 末尾的 bss 部分：即文件内容结束到 memsz 边界的部分。
  3. 零值填充：在调用 load_icode_mapper() 加载页面时，对于属于 .bss 段的内存区域，系统会为其分配物理页，并调用 memset 或类似的逻辑将其内容手动填充为 0，从而确保了未初始化全局变量的初值为 0。

Thinking 6.10

  1. MOS 中的 shell 命令：是外部命令。在 MOS 中，命令是以独立可执行文件的形式存在于磁盘上的，shell 通过调用 spawn 来创建子进程并加载这些文件执行。

  2. 为何 Linux 的 cd 是内置命令：因为 cd 命令的作用是切换 当前工作目录 (CWD)。当前工作目录是 进程特定 的属性。如果 cd 是外部命令，shell 会 fork 出一个子进程来执行它，子进程虽然切换了目录，但退出后不会影响父进程（即 shell 自身）的目录。因此，cd 必须由 shell 进程亲自执行，即作为内置命令。

难点分析

1. 管道（Pipe）

  • 共享与读写限定：管道是半双工的，只在有亲缘关系的进程间通信。两端使用不同的文件描述符页（rfd 和 wfd），通过重新映射，指向同一个物理页（Pipe 缓冲区），并用 fd_omode 精确约束各自的读写权限。
  • 时序竞争与状态判定：判断管道是否关闭（_pipe_is_closed）是本实验最大的难点。因为获取引用计数的操作不是原子的：
    • 在 close 时，必须 先解除 fd 的映射，再解除 pipe 的映射；
    • 在 dup 时，必须 先映射 pipe 页，再映射 fd 页。
    • 如果顺序反了，会在两次映射操作的间隙提前满足 $\text{pageref}(pipe) == \text{pageref}(fd)$ 的判闭条件，导致读进程误判提前返回 EOF。

2. Shell

  • 用户态加载（spawn）：相比内核态加载（Lab3），用户态需要自己手动加载并解析 ELF 格式。在实现 load_icode_mapper 时，难点在于正确识别并清零 .bss 段（即内存大小大于文件大小 memsz > filesz 的部分），必须配合使用 user_bzero 写入零值。
  • 内置与外部命令区分：比如 cd 必须是内置命令由 Shell 自身直接执行。如果通过 fork/spawn 生成子进程作为外部命令执行，子进程切换目录后会直接退出，不会影响父进程（Shell）的工作目录。
  • 复杂命令的多进程协同：在执行类似 ls.b | cat.b > motd 时，主 Shell 会先产生一个子 Shell 来统筹。子 Shell 内部再 spawn 两个子进程来执行命令。在多进程并发下，若不及时手动关掉自己不用的管道端，会导致读进程由于等不到 EOF 信号而陷入死锁。其全流程涉及 2 次 spawn 和 3 次进程销毁。

实验体会

通过本次实验，我深入理解了管道的实现机制，尤其是通过共享物理页实现进程间通信的细节，以及在多进程环境下正确管理资源和避免竞争条件的重要性。同时，用户态加载 ELF 文件的过程让我体会到了操作系统在程序执行前所做的准备工作，包括内存映射和段加载等。最后，Shell 的实现让我认识到命令解析、内置命令与外部命令的区别，以及在复杂命令执行中多进程协同的重要性。这些经验将对我今后深入学习操作系统原理和设计有很大帮助。
