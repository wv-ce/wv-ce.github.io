BUAA OS Lab4 实验报告

思考题

Thinking 4.1

  • 内核保存现场如何避免破坏通用寄存器： 内核在进入异常处理程序时，将当前栈指针或通用寄存器的值保存到内存中的 Trapframe 结构里，从而在不破坏其他通用寄存器的情况下完成上下文的持久化。

  • 能否直接从 $a0-$a3 获取 msyscall 信息： 可以。

  • 如何让 sys 函数获得一致的参数： 内核在调用具体的 sys_* 处理函数前，会根据 MIPS 的调用约定，将从用户态保存下来的参数（位于 Trapframe 中）重新加载到相应的寄存器或压入内核栈，使得 C 语言编写的内核函数能像接收普通函数调用一样，准确获取到用户通过 msyscall 传递的参数。

  • 系统调用对 Trapframe 的更改及其对用户态的影响： 内核主要修改 Trapframe 中的 EPC（将其加 4，指向 syscall 指令的下一条，避免死循环）；反映在用户态表现为：当程序从内核返回后，能够接着执行下一条指令，并从特定的寄存器中获取到系统调用的执行结果（如成功标志或返回的数据）。

Thinking 4.3

在系统调用和 IPC 的实现中，0 具有特殊的语义含义：

  • 当前进程的代称：在许多系统调用（如 sys_mem_alloc 或 sys_ipc_can_send）中，如果用户传入的 envid 为 0，内核通常会将其解释为“指向当前调用者进程自己”（current environment）。
  • envid2env 的特殊处理： 在 envid2env(u_int envid, struct Env penv, int checkperm) 函数中，有如下逻辑： 如果 mkenvid 可能生成 0，那么内核将无法区分用户是想通过真实的 ID 访问某个进程，还是想通过缺省值 0 访问当前进程，这会导致逻辑歧义。

Thinking 4.5

为什么子进程的 UXSTACK 必须重新分配，而不能共享或设为 COW？

  • 独占性与物理分离：UXSTACK 是用户态异常栈，专门用于处理写时复制（COW）引发的页写入异常。如果父子进程共享该栈或设为 COW，当子进程触发页错误进入异常处理时，其在 UXSTACK 上的压栈操作会立即触发另一个 COW 异常。这会导致嵌套异常甚至死循环，因为处理异常的工具本身就处于不可写的状态。
  • 上下文安全性：异常处理涉及寄存器状态的保存与恢复。若父子进程共用同一个 UXSTACK 物理页，两者的异常处理逻辑会互相覆盖对方栈上的数据，导致上下文损坏，系统崩溃。

为什么不应对 UVPT/VPT/VPD 等自映射区域调用 duppage？

  • 内核静态映射特性：在 env_init 阶段，内核已经为每个进程静态地设置好了 UVPT 等自映射区域。这些区域的页表项（PTE）是指向页表自身的。
  • 自映射逻辑冲突：duppage 的核心逻辑是将页表项标记为只读并设置 PTE_COW。如果对自映射区域（即页表本身所在的虚拟地址）调用 duppage，会导致以下错误行为：
    • 权限锁定风险：将页表页设为只读或 COW 可能会破坏硬件/内核更新页表的机制。
    • 递归错误：自映射区域的特殊性在于“以虚拟地址访问页表”。如果在拷贝过程中修改了自映射的映射关系，会导致子进程无法通过 UVPT 正确读取自己的页表，甚至指向父进程的物理页表页。
    • 冗余与不一致：内核已经保证了子进程拥有自己独立的页目录/页表结构（在 env_alloc 中通过 vpt/vpd 相关映射完成），手动调用 duppage 会导致映射关系混乱，甚至将原本应该指向子进程页表的 VPT 指向了父进程的物理页，造成严重的地址空间污染。

Thinking 4.6

vpd 是页目录的首地址，vpt 是所有页表的首地址。使用方式就是通过下表索引机制。比如想要访问页目录中的第一个页目录项，那么这一项的值就是 vpd[1]。

在 entry.S 中，这两个变量被设置为了 .globl ，即在用户进程中，这两个变量是全局变量，可以直接访问。

Thinking 4.7

“异常重入”发生在用户态程序在执行第一次异常处理程序时，又触发了另一次异常（如处理该 TLB 修改异常时再次发生 TLB 缺失），导致原本的现场被覆盖； 内核将 Trapframe 复制到用户空间是为了让用户态的异常处理函数能够保存并访问上一次异常发生时的现场信息，从而避免多次嵌套异常导致现场丢失，并支持后续正确恢复程序执行。

Thinking 4.8

  1. 内核精简与安全：将复杂的缺页处理逻辑移至用户态，减少了内核代码量，降低了内核出错导致整个系统崩溃的风险（微内核理念）。
  2. 灵活性高：用户程序可以根据自身需求定制页面置换、写时复制（COW）或内存映射策略，而非受限于内核预设的通用机制。

Thinking 4.9

在设置写时复制（COW）保护机制之前设置异常处理函数，是为了确保当进程触发第一次写入页面异常（TLB Mod）时，内核能通过正确的处理逻辑来接管并分配新的物理页。

如果延迟到该机制完成之后再设置：在设置完成前的这段“窗口期”里，若程序尝试写入被标记为只读的共享页面，系统无法找到注册的异常处理函数，操作系统会因为无法处理“非法写入”而直接报错或触发 panic，导致进程异常终止，从而无法实现预期的写时复制功能。

难点分析

  1. 函数是在用户态还是内核态执行。对实验中syscall_*、msyscall、sys_*函数的关系与实现的理解。同时需要注意函数参数的传递方式和调用约定，特别是在内核态如何从 Trapframe 中获取参数并传递给 C 语言编写的内核函数。
  2. fork函数的具体流程。

实验总结

  1. 通过本次实验，我深入理解了系统调用的实现机制，特别是用户态与内核态之间的交互方式，以及如何通过 Trapframe 来保存和恢复上下文。
  2. 对fork函数的实现流程有了更清晰的认识，理解了进程创建、资源复制以及异常处理等关键步骤。
